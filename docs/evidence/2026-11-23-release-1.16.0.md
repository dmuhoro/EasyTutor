### Lighthouse: load-sensitive re-measurement recorded honestly

The five green Sprint 33 runs on the **byte-identical** bundle were `/` 89–92 and
`/login` 90–92 with TBT 180–220 ms
(`docs/evidence/2026-11-23-lighthouse-80.md`). At release time the fail-closed gate was
re-run on this host and **failed twice**:

```
/       performance=70/100  TBT=540 ms   (load average 2.74 / 3.46 / 2.68)
/login  performance=73/100  TBT=480 ms

/       performance=75/100  TBT=440 ms   (load average 2.73 / 3.41 / 2.69)
/login  performance=80/100  TBT=350 ms
```

The gate behaved correctly: it exited 1 and named the failing routes. The host had a
sustained load average of ~2.7 with a user-owned Chrome renderer at ~83% CPU; those browser
processes were deliberately **not** terminated because they belong to the user's session.

Evidence that the app code did not change between the green and red measurements:

```
dist/_expo/static/js/web/entry-c54585ef6e7aa001781a072b36ab1688.js   (same in both)
dist/_expo/static/js/web/index-6ed863452030ef58b17b0f40b80ec3f8.js   (same in both)
```

The release commit changes only version metadata and truth documentation; no shipped
JavaScript changed. The scores are therefore recorded as **load-sensitive local
measurements**, not as a new product result. The verified claim remains the five Sprint 33
runs on the identical bundle. No budget, threshold or test was lowered to make either
release-time run pass.
